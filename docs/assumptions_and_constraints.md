# Assumptions and Constraints

Assumptions are choices made that could turn out to be wrong. Constraints are limits imposed on the project that were not chosen. Keeping these separate matters: an assumption is something worth re-checking if the project's context changes; a constraint is a fixed given.

## Assumptions

- Spark and PostgreSQL run on the same machine, so no network latency or partitioning between them was accounted for
- The system clock is accurate and synchronized - `event_timestamp` validation (rejecting timestamps more than 5 minutes in the future) depends on this
- The CSV schema generated by `data_generator.py` never silently changes shape (same columns, same order) for the life of this project
- The generator always produces valid UTF-8 text (no encoding edge cases were tested)
- Available disk space is sufficient for the data/incoming/, data/processed_archive/, and data/rejected/ folders during any single test session
- The event volumes used in testing (up to ~800 events per run) are representative enough to surface real performance characteristics, even though they are far below genuine production e-commerce traffic

## Constraints

- CSV files must be used as the streaming source instead of Kafka or another message queue - this is a requirement of the assignment brief, not a technical limitation of the tools involved
- Processing is micro-batch based (Spark Structured Streaming's model), not true row-by-row continuous processing
- A single PostgreSQL instance is used; there is no replication, failover, or clustering
- Development and testing were performed on a single Windows machine with limited, non-dedicated hardware resources shared with other running applications

# Risks and Limitations

Distinct from Future Improvements: this document lists what the system genuinely cannot do or has not been proven to do, as of this submission. Future Improvements lists what COULD be added later.

## Risks

| Risk | Mitigation in Place | Residual Risk |
|---|---|---|
| PostgreSQL becomes unreachable mid-batch | Files remain unarchived, retried on next trigger (see error_handling_and_recovery.md) | No exponential backoff; a persistently-down database would cause the same batch to be retried indefinitely at a fixed interval, generating continuous log noise without escalating |
| Disk fills up (data/incoming/, data/processed_archive/, checkpoint/ all grow over time) | Archiving keeps data/incoming/ small; no retention/deletion policy exists for data/processed_archive/ or logs/ | Long-running deployments would need a retention policy (see retention_policy.md) - not implemented, only documented as a gap |
| Large batch sizes | repartition(4) fix reduced connection overhead significantly (see performance_metrics.md) | Not tested beyond ~60 rows/batch; behavior at genuinely large batch sizes (thousands of rows) is unverified |
| Schema drift (generator's CSV columns change unexpectedly) | Explicit schema declaration means a genuinely missing/renamed column would produce nulls, which existing validation would catch as missing_or_invalid_* | Column REORDERING or a wholly different file format would not be handled gracefully |
| Windows file locks (observed directly during this project) | main.py clean now uses ignore_errors=True and reports failures instead of crashing | Underlying cause (OneDrive sync, possible lingering Java processes) not fully eliminated, only worked around defensively |

## Limitations

- **Zero-row files are never archived - three separate fixes were attempted, and specifically why each one fails is now documented.** A CSV file that is empty or contains only a header row (no data rows) is read correctly and produces no crash, but `archive_source_files()` determines which files to archive by inspecting the `_source_file` column of the batch's ROWS - a file with zero rows has no row referencing it, so it is never moved to `data/processed_archive/`. It remains in `data/incoming/` indefinitely (though it is also never reprocessed, since Spark's checkpoint tracks seen files independently of row count).

  A fix was attempted using `DataFrame.inputFiles()` - Spark's own record of which files were physically scanned to produce a DataFrame, independent of row count. This was verified to work correctly on a plain BATCH read (`spark.read.csv(...)`): a direct test confirmed `inputFiles()` correctly listed both a 0-byte file and a header-only file even though `df.count()` was 0.

  However, the SAME approach fails inside the actual streaming pipeline: the DataFrame Spark hands to `foreachBatch()` for a zero-row micro-batch returns `inputFiles() == []` - completely empty - even though that exact batch demonstrably detected and processed those files (confirmed via a debug log line placed directly in `archive_source_files()`). This means Structured Streaming's per-batch DataFrame (backed by `FileStreamSource`) does not populate `inputFiles()` the same way a plain batch read (backed by a standard `DataSource`) does, at least not for a batch producing zero output rows. This is a genuine, specific, confirmed Spark internals difference between streaming and batch DataFrames - not a mistake in the fix's logic, which was independently verified correct in isolation.

  The `inputFiles()` fix was reverted rather than shipped, since deploying something that had already been proven not to work in the actual pipeline would be worse than keeping the original, understood limitation. A real fix requires tracking files via the filesystem directly (list `data/incoming/` before a trigger, archive exactly those files after success) rather than via any DataFrame-level file metadata - a larger, more careful change than a one-line swap, listed in `future_improvements.md` rather than rushed.

  A THIRD fix was then attempted, using Spark's own built-in file archiving instead of anything DataFrame-derived: `.option("cleanSource", "archive")` together with `.option("sourceArchiveDir", ...)` on the streaming read. This approach got materially further than the previous two. Unlike row-content inspection and `inputFiles()`, `cleanSource` operates at the file source level, independent of row count, and testing confirmed it DOES correctly identify zero-row files as files to archive - the targeting problem that defeated both earlier attempts is genuinely solved by it.

  It nevertheless fails on Windows, at the final step of actually moving the file. Spark's `SourceFileArchiver` builds the destination path by nesting the source file's full original absolute path underneath the archive directory - drive letter and all - producing a path shaped like `processed_archive/C:/Users/.../data/incoming/events_batch_1.csv`. Windows rejects this, because a colon cannot appear inside a folder name, and the archive step dies with `Mkdirs failed`. This is a genuine bug in Spark's own Scala implementation (`FileStreamSource$SourceFileArchiver`), in how it constructs the destination path - not a misconfiguration on our side and not something correctable from Python, since the path is assembled internally by Spark with no hook to override it. As with the `inputFiles()` attempt, this was reverted rather than left in place half-working: the option would have silently identified the right files while failing to move any of them, which is strictly worse than the original, understood limitation.

  An open question, deliberately not stated as a claim: this may well work correctly on Linux or macOS, where absolute paths have no drive-letter prefix and therefore no colon to collide with the nested-path construction. That was NOT tested here - the pipeline was only ever run on Windows - so whether `cleanSource=archive` is a viable fix on a non-Windows environment remains unverified either way, and is listed in `future_improvements.md` as something to confirm rather than something to assume.


- **CSV-based simulation, not real streaming infrastructure.** This is an explicit, accepted constraint (see scope.md), not a limitation discovered after the fact - but it means findings here (throughput, latency) describe THIS specific architecture and would not directly transfer to a Kafka-based system.
- **Single-machine testing only.** No distributed Spark cluster or networked PostgreSQL instance was tested; latency and throughput numbers in performance_metrics.md reflect local-machine conditions only.
- **No automated tests for system-level failure scenarios** (database outage, mid-batch crash, deliberately corrupted CSV) - see test_cases.md's "System-Level Scenarios" section for the explicit list of what was and was not tested, and why.
- **No connection pooling.** Each partition opens and closes its own psycopg2 connection per batch. This was identified as the dominant cost in per-batch latency (see performance_metrics.md) and is listed as a concrete future improvement rather than fixed in this version.
- **Trigger interval tuning was not iterated on.** The configured 5-second interval was found to be too aggressive for the tested write pattern; a properly tuned value was not re-tested after this finding, due to time constraints (see performance_metrics.md).
- **No security hardening.** Database credentials are read from a local .env file (gitignored), but postgres_connection_details.txt (a required deliverable per the original brief) does store connection details as a checked-in file - see engineering_decisions.md's note on this explicit, documented trade-off.
- **CORRECTED FINDING: the previously-reported "stream_metrics.num_input_rows shows a consistent 3x multiplier" was very likely a measurement artifact, not a real bug.** The original diagnostic queries (both the initial discovery and this project's earlier documentation of it) selected from stream_metrics WITHOUT filtering by run_id. Since batch_id resets to 0 on every new streaming run, any test session that restarted the streaming job even once (a crash, a manual restart, an interrupted test) would produce a SECOND set of rows also starting at batch_id=0, silently mixed together with the first run's rows in any unfiltered query - exactly the kind of contamination that would produce a seemingly consistent, reproducible-looking multiplier.

  This was re-investigated properly: a controlled 4-batch test run, queried with an explicit `WHERE run_id = '<the exact run's id>'` filter, showed num_input_rows matching the true valid+rejected count EXACTLY for every batch (20↔20, 40↔40, 20↔20, 40↔40) - no multiplier at all. The `.persist()` fix suggested by a peer implementation (caching the shared upstream DataFrame before multiple actions run, to prevent genuine Spark lineage recomputation) was investigated as a possible cause, but was not needed or applied, since the bug did not reproduce under correct, run_id-filtered measurement.

  This is kept in the documentation as an explicit correction, not silently removed, since the original (incorrect) claim was itself documented previously - an honest record should show what was believed, what new evidence contradicted it, and why the corrected conclusion is now trusted. Anyone querying stream_metrics for analysis should always filter by run_id explicitly; failing to do so will produce misleading, inflated-looking numbers whenever a test session has more than one run in its history, which is likely most of the time during development.

  A defensive persist()/unpersist() (wrapping the shared batch_df for the duration of process_batch(), in a try/finally block) was added to spark_streaming.py around the same time as this investigation, matching a pattern used in a peer implementation to prevent redundant re-reads of a shared upstream DataFrame. Three separate controlled multi-batch test runs were performed - two WITH this persist() code active, one WITHOUT it beforehand - and all three showed num_input_rows matching the true row count exactly, with no multiplier in any of them. This means the evidence does not show persist() was NECESSARY to fix the originally-claimed bug (since the bug did not reproduce even without it); it is kept as a reasonable, low-risk defensive addition on its own merits, not as a verified fix for a confirmed problem.

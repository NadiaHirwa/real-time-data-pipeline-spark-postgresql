# Engineering Decisions

For every significant technical choice in this project: what we chose, why, what the alternative was, and what trade-off we accepted. This is meant to be read on its own - a reviewer should understand *how* this pipeline was designed, not just *what* it does, from this document alone.

| Decision | Reason | Alternative | Trade-off |
|---|---|---|---|
| Spark Structured Streaming | Native support for continuous file ingestion, checkpointing, and recovery - directly matches the course's Structured Streaming curriculum | Plain batch Spark run on a schedule (e.g. every 5 minutes via cron) | More upfront complexity (checkpointing, streaming-specific schema rules), but genuinely near-real-time rather than a delayed batch |
| File-based source (CSV in a landing folder) | Required by the assignment brief | Kafka, a message queue | Simpler to set up locally, but less realistic than a true streaming source; explicitly documented as a limitation, not hidden |
| foreachBatch() + JDBC write, rather than any "streaming JDBC sink" | Spark Structured Streaming has no native streaming sink for JDBC/relational databases | A custom ForeachWriter writing row by row | foreachBatch is the standard, documented Spark pattern for this exact problem; per-row writes would be dramatically slower and are not idiomatic |
| Explicit schema declared up front, no schema inference | Structured Streaming cannot infer a schema from files that haven't arrived yet - inference requires seeing the data first, which is incompatible with an open-ended stream | Schema inference (works fine in batch mode, as used in Lab 1) | Slightly more upfront definition work, but required for streaming to function at all, not a stylistic preference |
| PostgreSQL | ACID compliance, relational integrity via constraints, mature and simple JDBC driver support | MySQL, SQLite | Comparable to MySQL in practice; chosen because it's already installed and working locally |
| Native PostgreSQL install as the primary path (Docker added later as an additional option, not a replacement) | PostgreSQL was already installed and working from a prior project, and the native setup is what every performance number here was measured on | A Dockerized Postgres instance from the start | Originally accepted as less portable in exchange for not adding a new tool; that portability gap was later closed by the Docker Compose setup below, which runs the same code without replacing the proven native path |
| Dedicated rejected_events table for invalid records | Bad data should remain inspectable for debugging and auditing, not silently discarded | Filter and drop invalid rows with no trace | Slightly more storage and one more table to manage, but mirrors how real production pipelines handle data quality failures |
| Checkpointing treated as a hard requirement, not optional | Checkpointing is what makes Structured Streaming recoverable after a restart - without it, the "streaming" claim is largely cosmetic | Skip checkpointing, accept full reprocessing of all historical files on every restart | None meaningful - this is treated as a correctness requirement rather than a nice-to-have |
| At-least-once delivery semantics, not exactly-once | foreachBatch + a JDBC insert is inherently at-least-once: if a batch partially writes and then fails, a retry can reinsert some rows | A fully transactional, exactly-once sink (e.g. a two-phase commit pattern) | Accepted and explicitly documented; mitigated in practice with a unique constraint on event_id and an ON CONFLICT DO NOTHING upsert, so duplicates cannot actually land in the final table even if delivery retries |
| event_timestamp (from the generated timestamp) tracked separately from ingested_at (processing time) | These can genuinely differ if a file arrives late or is delayed, and conflating them would make performance/latency measurement meaningless | Use only one timestamp for both purposes | One extra column to maintain, in exchange for being able to honestly measure pipeline latency (ingested_at minus event_timestamp) |
| `postgres:16-alpine` pinned specifically - not `latest`, and not `18` | postgres:18 changed the image's default PGDATA path. A volume mounted at the old location would still appear to work, then silently lose the database on the next container recreate - a data-loss failure mode with no error message. Pinning a known major version makes the mount location predictable; alpine keeps the image small | `postgres:latest`, or an unpinned `postgres` | Must consciously decide when to move to a newer major version, rather than drifting into one - which is the entire point, since that drift is exactly what causes the silent breakage |
| Named volumes for both `postgres_data` and `spark_checkpoint`, rather than bind mounts | Two independent, well-documented problems. PostgreSQL's data directory needs POSIX ownership and permissions that a Windows bind mount cannot represent. Spark's checkpointing depends on atomic rename semantics that Windows bind mounts do not reliably honour, and the failure mode there is rare, silent checkpoint corruption rather than a clean error | Bind-mounting both to host folders, so their contents are directly browsable | Contents are not inspectable from the host file explorer and are managed through `docker volume` commands instead. `./data` is deliberately still a bind mount, because generated and archived CSVs genuinely do need to be visible on the host |
| `depends_on` with `condition: service_healthy` for the app service, not a bare `depends_on` | A bare `depends_on` waits only for the Postgres container to START, which happens well before Postgres accepts connections - and on first run the server restarts partway through initdb, so the gap is large. The app would connect too early and crash | Bare `depends_on`, or a retry/sleep loop in application code | Requires a healthcheck on the Postgres service (`pg_isready`) and a `start_period` generous enough for first-run schema initialization; in exchange, startup ordering is handled by the platform rather than by defensive code in the app |
| JDBC driver baked into the Docker image at build time, while the native path keeps resolving it from Maven at runtime | Baking it in makes container startup deterministic, offline-capable, and measurably faster (no Ivy resolution on every start). But the native path's Maven resolution already works across Windows, Linux, and CI and should not have to change | Downloading the jar at container start; or switching both paths to a baked/vendored jar; or an `if running_in_docker()` check | Implemented as a single environment-variable fallback in `with_postgres_driver()`: `POSTGRES_JDBC_JAR` set means use that local jar, unset means use Maven coordinates. Neither path needed logic about the other, and callers (the streaming job and the pytest fixture) share one helper. The cost is that the version appears in two places - `POSTGRES_JDBC_COORDINATES` and the Dockerfile - which must be kept in sync, so each is commented pointing at the other |
| `archive_source_files()` converts `file://` URIs with `urlparse` + `url2pathname`, replacing a string-replace approach | A genuine cross-platform correctness bug, found only because Docker Compose was the first time this code ran on Linux. The old `file_uri.replace("file:///", "")` worked on Windows purely by coincidence: `file:///C:/path/x.csv` becomes `C:/path/x.csv`, still absolute, because a Windows path carries a drive letter right after the scheme. On Linux, `file:///app/data/x.csv` becomes `app/data/x.csv` - the leading slash is consumed, producing a RELATIVE path. `Path.exists()` then quietly returned False, so archiving silently did nothing: no exception, no log line, just files accumulating in data/incoming/ forever | Keeping the string-replace and special-casing Linux; or stripping only `file://` (two slashes) instead of three | None - the proper conversion is correct on both platforms and additionally decodes percent-escapes, which the old code mangled (a directory containing a space arrives from Spark as `%20`). Worth recording as a category, not a one-off: a Windows-only test surface can hide a platform assumption indefinitely, and containerizing exposed this one immediately |
| Retry/error-classification logic inlined directly inside make_write_valid_partition, not imported from separate errors.py/retry.py modules | Functions passed to foreachPartition run in separate worker subprocesses on Windows local[*], which don't inherit the driver's sys.path - a worker trying to import retry fails with ModuleNotFoundError, crashing the worker outright rather than raising a catchable Python exception | Modular errors.py/retry.py files, importable normally (kept in the repo for driver-side code, e.g. a future staging-table rewrite) | Some code duplication if this pattern is needed elsewhere; accepted since correctness on the worker matters more than DRY-ness here |

## Standing Rule: Null-Sensitive Comparisons Need an Explicit isNull() Guard

Two real bugs were found (via comparison with a peer implementation, then confirmed with failing tests before fixing) in tag_validation_result(): `~F.col("event_type").isin(...)` and `~F.col("event_id").rlike(...)` both silently failed to reject a genuinely NULL value. This is not a mistake specific to those two lines - it is how Spark's three-valued (NULL-aware) logic works for an entire category of operations: `isin()`, `rlike()`, and most comparison operators return NULL (not True or False) when the input itself is NULL, and a negated NULL (`~NULL`) is still NULL. A `.when(NULL, ...)` condition never matches, so the row silently falls through to later checks - or, if nothing else happens to catch it, is incorrectly treated as valid.

The fix is always the same shape: `F.col(x).isNull() | <the original condition>`, since `isNull()` itself is null-safe (it always returns a real True or False, never NULL). Every condition added to `tag_validation_result()` going forward must be checked against this pattern specifically for any column that can legitimately be NULL after casting - not just assumed safe because it "looks like" a normal boolean check.

## Standing Rule: No Custom Module Imports Inside Worker-Bound Closures

Any function passed to foreachPartition() or used inside foreachBatch()'s per-row/per-partition logic must be fully self-contained. It may only reference:

- Genuinely pip-installed third-party packages (psycopg2, pyspark itself)
- Python standard library modules (random, time, etc.)
- Plain values (strings, numbers) captured directly in its closure

It must NEVER reference a custom project module (config, errors, retry, monitoring_logger, etc.) by name inside its body - even via an import statement placed at the top of the file containing the closure. This bug was hit twice during development: once with config.DB_HOST referenced directly inside a partition-writer function, and once with an imported with_retry function referenced the same way. Both manifested as Spark's generic, hard-to-diagnose "Python worker exited unexpectedly (crashed)" error rather than a clear Python traceback, since the worker process fails during closure deserialization, before any of the function's own code has a chance to run.
